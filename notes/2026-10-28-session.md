# Session 2026-10-28: CEX loader

## Done

First step: load and parse the 8 blocks of the `mousike` release
(`https://raw.githubusercontent.com/neelsmith/mousike/refs/heads/main/releases/current.cex`).

Layout under `src/` (no dependencies; Node 18+ only for tests/build):

- `lib/cex.js` — parser. Classic UMD script (global `AgmCex` in browser, CommonJS in Node),
  so the built page works from `file://`. `parseCex(text)` returns
  `{ version, images, surfaces, audio, texts, notes, syllables, dse, index, warnings }`.
  - Rows are objects keyed by header column names.
  - `texts`/`notes`/`syllables` rows also get `work` and `passage` (split CTS URN).
  - `notes` rows get `tokens`: array of note groups; `~` joins notes on one syllable.
  - CITE2 URNs (`parseCite2`): `urn:cite2:NS:COLLECTION[.VERSION]:OBJECT[@ROI]`. The last
    part is the object id; a 4-part URN is a collection (object = null). ROI parsed as
    `{left, top, width, height}` (fractions). Neel described ROI as `t,l,w,h`, but in the
    data the 1st value varies across a line and the 2nd line by line, so the code treats
    it as left,top. Confirm with Neel.
  - `images` rows get `cite2`; `dse` rows get `cite2`, `imageObject` (URN minus ROI), `roi`.
  - `resolveImage(images, ref)` matches namespace + collection + object (any version if the
    reference omits one).
  - `index.{images,surfaces,texts,notes,syllables}` are `Map`s keyed by URN.
  - Missing/unknown blocks, header mismatches, bad column counts, duplicate URNs → `warnings`.
  - `loadCex(url, fetchImpl?)` fetches + parses.
- `lib/app.js` — UI: loads default URL on start, URL box + local-file fallback, summary
  counts, warnings, collapsible table per block. Parsed data at `window.agm.data`.
- `app.html` — template; `build.js` inlines both scripts → `dist/agm.html` (single file).
- `test/cex.test.js` + `test/fixtures/current-2026a.cex` (snapshot of release 2026a).

Commands (from `src/`): `npm test`, `npm run build`.

## 2026-10-29: artifact (surface) menu

- `lib/edition.js` (global `AgmEdition`), pure query functions over parsed data:
  - `surfaceMenu(data)` → `[{urn, label}]`
  - `dseForSurface(data, surfaceUrn)` → DSE rows whose `surface` equals the URN
  - `resolvePassage(data, urn)` → `{urn, block: "texts"|"notes"|null, match, record}`.
    `match` is `"exact"`, `"container"` (URN not present, but a parent passage such as
    `notes:1` for `notes:1.1` is; returned for context only), or `null`.
  - `surfaceContents(data, surfaceUrn)` → `{surface, entries:[{dse, passage}], counts}`
- UI: "Artifact" `<select>` of surface labels; choosing one lists each DSE record with a
  short ref (`notes:1.1`, full URN on hover), its image region, and the resolved content.
  Unresolved entries are marked, and the containing passage is shown when there is one.
  Raw block tables are now inside a collapsed "Release data" panel.
- `window.agm.selectSurface(urn)` / `window.agm.accept(data, source)` are exposed;
  `window.AGM_NO_AUTOLOAD = true` before the app script skips the initial fetch.
- `npm run preview` → `dist/agm-fixture.html`: the app with the 2026a fixture inlined and the
  first surface selected, for checking the UI offline. Checked by screenshot at phone width.
- Notes citation (clarified by Neel): `#!notes` is cited by line, like `#!texts`. A 2-tier
  citation `notes:L.N` = the Nth whitespace-separated note group in line L (analogous to
  `syllables:L.N`); notes within one group are joined by `~`. `cex.noteGroups()` derives
  these; `data.index.noteGroups` maps `…notes:L.N` → `{urn, line, group, notes[], text}`.
  `resolvePassage` returns `unit: "line" | "group"`. UI shows a group's notes joined by
  ` ~ ` with "(n notes on one syllable)" when n > 1.
- 2026a: 29 note groups (5+7+8+9), same as the syllable count.
- With 2026a data: 34 DSE records for the stele → 20 exact (notes:1.1–4.5), 5 container
  (text:1.1–1.5; texts are line-level only, so these show text:1), 9 missing
  (notes:5.x–6.x: notes has only 4 lines). Open question for Neel: should `text:L.N` DSE
  refs resolve to syllables, or are they meant to be syllables URNs?

## 2026-10-29: regions of interest on the image, linked to the line view

- `viewer.js`: `setRegions([{id, roi, kind, title}])`, `highlight(id|null)`, `onRegionHover(fn)`.
  Regions are HTML boxes in an overlay; `apply()` recomputes their screen boxes with
  `regionBox(state, imgW, imgH, roi)` on every pan/zoom (outline width stays constant).
  Hover callbacks are suppressed while dragging.
- `edition.js` `imageRegions(data, surfaceUrn, imageUrn)` → `[{id: dse.text, roi, kind, dse}]`;
  kind = notes | syllables | texts | other (passage not found).
- `app.js`: line-view note groups and syllables carry `data-urn` (their passage URN) via
  `linked()`. `highlight(urn)` (also `window.agm.highlight`) marks `.hl` on matching line-view
  elements and `active` on matching regions; hovering either side calls it. Elements that have a
  region on the current image get `.has-roi`. Key below the viewer: amber = notes, cyan = syllables,
  white = DSE passage not found (the 9 `notes:5.x`/`6.x`); active = red fill.
- ROI interpreted as left, top, width, height (fractions). With a stand-in image the boxes come out
  as rows with note boxes just above the syllable boxes, consistent with that reading.
- Known data caveat: DSE `notes:L.N` follow stele lines, the line view follows `#!notes` verse
  lines, so from line 2 on hovering a note highlights the region for a *different* note group

- Not done: touch has no hover (tap-to-link would be needed); hovering a region doesn't scroll the
